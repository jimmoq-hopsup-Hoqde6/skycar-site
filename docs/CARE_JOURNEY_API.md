# Connected service journey — implementation draft

Implemented on the isolated journey branch, not deployed to staging. The database migration is `supabase/migrations/20261003064126_care_connected_journey.sql`; disposable PostgreSQL and mocked browser acceptance passed. Hosted database/API/storage acceptance remains outstanding. See CARE_JOURNEY_CHECKPOINT.md for current evidence and CARE_JOURNEY_HOSTED_ACCEPTANCE.md for the release test procedure.

## Routes

- GET /api/v1/care/journey/:id — owner session or request-specific guest HttpOnly cookie. Returns request summary, reviewed quotes, current booking stage, recorded events and bounded private photo counts.
- POST /api/v1/care/journey/:id — same authority, trusted origin, UUID Idempotency-Key. Actions update_details, select_quote, request_cancel. Customer selection requests an appointment; it does not confirm capacity or take payment.
- POST /api/v1/care/journey/:id/photos — owner session or guest cookie, trusted origin; multipart photos, at most three JPEG/PNG/WebP images, each <=900 KB. Immutable manifest/slots preserve partial-upload recovery.
- GET /api/v1/care/journey/:id/photos/:slot — verified customer or admin; private/no-store binary image, never a public storage URL. This proxy route is the only display path; there is no signed-URL route.
- POST …/photos is limited per signed-in account to 10 **successfully recorded photo sets** per hour (fixed window, atomic database counter). A slot is reserved atomically before anything is stored (`care_reserve_photo_upload_slot`) and released (`care_release_photo_upload_slot`) on any failure: invalid, oversized or CSRF-rejected bodies, storage/marker 503s, conflicts and replays. Only the call that records the request's photo marker keeps its slot, so an identical retry after a 503 counts once, and re-sending an already recorded set is free (even at the limit; such a call never reserves). The eleventh new set in a window returns 429 `RATE_LIMITED` with `Retry-After` seconds and `retryable:true`; nothing is stored. A crash between reserve and release leaves the slot held until the window ends (conservative). Re-sending a recorded set touches no Storage and no quota: the marker holds the SHA-256 of the manifest, and the route hashes the validated body and compares it to the marker before any Storage call. An identical set returns 201 `{stored:n}` with zero Storage I/O; a different set returns 409 `IDEMPOTENCY_CONFLICT`, also with zero Storage I/O. No separate replay throttle is added: a replay costs one primary-key read plus hashing a body already capped at 2.8 MB, with no Storage I/O or writes, so rejected or replayed bodies are bounded by the body cap and platform request throttling. Guest-cookie uploads and admin completion evidence (`?kind=completion`) take no quota (their sets are write-once). If the counter cannot be read the upload fails closed with 503. The limit bounds stored sets, not request volume: rejected bodies are bounded by the 2.8 MB body cap and platform request throttling.
- `GET /api/v1/care/requests` items (and `care_list_requests`) include `photo_count` (0-3) and `has_photos`. They come from the write-once `care_request_photo_sets` marker that only the trusted photo route sets (service_role `care_record_request_photos`) after Storage confirms the manifest. The marker also stores the manifest SHA-256 and a request kind (`account`, or `guest` for guest intake requests, which take no quota). Only account markers feed the list projection. If the marker write fails (503) and the journey then leaves `review`/`quotes_ready`, `has_photos` stays false until the owner re-sends the identical complete set: the route then verifies the stored set read-only (no writes) and records the marker, counting one slot. A different or partial set still returns `INVALID_TRANSITION`. Admin completion evidence is not covered by the marker. Requests photographed before migration 20261101130000 have no marker until the identical photos are re-sent, so they report 0.
- GET /api/v1/operations/care — verified admin session; bounded queue and expert registry.
- POST /api/v1/operations/care — verified admin, trusted origin, UUID Idempotency-Key. Create expert, publish quote, confirm booking, start work, complete work, cancel booking.
- GET /operations/care — private admin workspace over the operations endpoints. Request selection, unsaved evidence and uncertain commands are cleared when the verified operations account changes.

All writes derive actor authority from server-verified sessions or a verified guest capability; browser actor IDs and roles are never trusted. The database rechecks administrator/customer authority. Unknown body fields, invalid prices/times and unsupported transitions fail closed. Commands, projection changes and events are transactional. Provider capacity is locked and checked for overlapping confirmed/in-progress appointments. No fixtures or invented assessments are returned by hosted APIs.

The guest receipt establishes its cookie only after successful intake and selected photo uploads. The link is usable in that browser. Cross-device recovery and outbound notification delivery require a separate verified contact channel.
